# Design tokens: two layers, oklch, single file

The dashboard's styling moves from 13 flat hex tokens to a two-layer token system in `packages/ui/src/design-system/tokens.css`: theme-independent **primitive ramps** (`--dash-stone-*` warm neutrals, `--dash-accent-*`, numeric `--dash-space-*`) defined once in `:root`, and a **semantic layer** (`--dash-surface`, `--dash-text-muted`, `--dash-state-*`…) redefined per theme (`:root` dark, `[data-theme='light']`), encoded in `oklch()`.

The palette (wayfinder "Palette candidates", C — Slate Steel) resolved single per-theme values; encoding them in OKLCH lets the ramps interpolate cleanly around those anchors so future steps (hover tints, chip backgrounds, chart series) derive rather than improvise. Component styles consume only **semantic color tokens** — never the color ramps directly — so a palette retune touches one file. The theme-independent scale primitives (spacing, type, radius, motion) are consumed directly by recipes: they are the contract, not a retune surface. Hex equivalents stay documented in DESIGN.md for reference. Job-state colors are intentionally semantic-only (six fixed meanings, no ramps). This is the base the `.dash-*` recipe layer and the App.css migration build on.
