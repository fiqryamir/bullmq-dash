# better-web-ui project context

## Design Context

### Users

Developers — both equally:

- **Local dev**: a developer glances at their own machine's queues while building, needing quick orientation and search.
- **Production monitoring**: ops/backend engineers watch live queues in shared environments, scanning tables of jobs, spotting failures, and digging into a job's data, logs, and retries.

The job is: "see what my queues and jobs are doing right now, and get to the one that matters fast." The UI must therefore be search-first, dense enough to scan, and calm enough to live on screen all day. Secondary audience: anyone embedding bullmq-dash in their own app must not have the dashboard fight their host's look — it should feel self-contained and unobtrusive.

### Brand Personality

Technical, calm, precise. Voice is neutral and matter-of-fact — no marketing flourish, no playfulness, minimal conversational filler. The interface should evoke confidence and quiet competence: you can trust what it reports because it never shouts.

### Aesthetic Direction

- **Reference**: Zen Browser — soft, muted, airy surfaces; gentle gradient accents; glassy translucency; rounded corners; tranquil overall feel. The dashboard should feel like a calm place to work, not a blinking ops console.
- **Anti-references**: harsh neon status lights, aggressive saturation, "cyber" dark UIs, dense cluttered grids with hard dividers everywhere, generic purple-on-black dev-tool styling (the current state).
- **Theme**: dark-first (default) with light as a first-class citizen — both fully tokenized, both WCAG AA.
- **Palette**: desaturated neutrals with gentle depth (surface → elevated surface), a quiet accent (soft blue/teal-family rather than the current saturated purple), and one distinct retuned color per job state (waiting, active, delayed, completed, failed, paused) that stays legible on both themes.
- **Shape**: gently rounded corners (12px panels, 8px controls, pill chips/tabs), consistent with the current geometry.

### Implementation Defaults

- **Framework / runtime**: React 19 SPA, Vite 7, TypeScript strict (`packages/ui`). Detected from codebase.
- **Styling**: plain CSS with CSS custom properties in `src/design-system/tokens.css` (`--dash-*` tokens, `:root` dark + `[data-theme='light']`). No Tailwind, no CSS-in-JS — future UI work must keep the token approach and the `data-theme` switch. Detected from codebase.
- **Component library**: Base UI (`@base-ui-components/react`, rc) — the project is Base UI-flavored, not Radix. Detected from codebase.
- **Headless ecosystem**: Base UI-flavored. Detected from codebase.
- **Tables**: TanStack Table (`@tanstack/react-table` v8) for job tables. Detected from codebase.
- **Virtualization**: TanStack Virtual (`@tanstack/react-virtual` v3) for long result lists and the command palette. Detected from codebase.
- **Forms**: no form library — inputs are plain search fields; no form stack to preserve. Detected from codebase.
- **Fonts**: system UI stack (`'Segoe UI', system-ui, -apple-system, sans-serif`) with `ui-monospace, Consolas, monospace` for IDs, code, and logs. Detected from codebase.
- **No `components.json` / shadcn**: not a shadcn project. Detected from codebase.
- **Config**: `packages/ui/src/config.ts` reads a `UIConfig` (board title, polling interval) — embedding contract lives in `src/api/contract.ts`.

### Design Principles

1. **Calm surfaces, quiet accents.** Use desaturated neutrals and gentle depth for hierarchy before color; the accent carries focus, not decoration. Avoid saturated fills and neon — Zen-like restraint.
2. **State colors mean something — retune, don't remove.** Each job state keeps one distinct, WCAG-AA-legible color, tuned per theme. Chips/tabs carry state; nothing else should compete with them.
3. **Density with breathing room.** Tables and lists are the product: tight rows, sticky headers, monospace data, but with airy spacing and soft separators so long monitoring sessions stay readable.
4. **Search-first, one clear path.** The command palette and search bar are the fastest route to a job; every screen should have one obvious primary action, with destructive/state-changing actions visually secondary.
5. **Both themes are first-class.** Every new component must be defined in tokens for dark and light from the start — never dark-only — and keyboard navigation and focus states must not rely on color alone.
